## 1. BuilderInvoice → stored Invoice mapping

| Builder (`features/invoice-builder/types.ts`) | Stored (`types/invoice.ts` + `Business`) |
|---|---|
| `invoiceNumber`, `issueDate`, `dueDate`, `currency`, `notes` | Same fields on invoice doc |
| `customer.name/email/address` | `clientName`, `clientEmail`, `clientAddress` (denormalised) |
| `business.*`, `logoDataUrl` | Separate `Business` doc (`businessName`, address, `logoUrl`); create minimal business on first save if missing |
| `payment.*` (IBAN/SWIFT-shaped) | `business.bankDetails` (UK sort/account) — map best-effort; do not invent fields |
| `templateId` | Persist on invoice if we add `templateId` field, else keep in builder session + settings branding for account PDF until schema extended. **Decision for B1:** store `templateId` on the invoice document (additive field; rules already allow create/update of owned invoices). |
| Line `discountType` | On `InvoiceItem`; server defaults missing → `"percent"` |
| Totals | Not on builder; compute via `calculateInvoiceTotals` and write `totals` + per-line computed amounts on save |
| Status | Builder has none; first save → stored as unpaid-facing status (see §5 mapping): use `sent` or keep `draft` then surface as Unpaid. **Decision:** save as `sent` for “Unpaid” UX, or `draft` if we map draft→Unpaid. Prefer **`draft` → Unpaid** in History UI so autosave does not imply “sent”. |
| `customerId` | Always `""` on create today; keep empty; rely on client* fields |

## 2. Routes today vs `/create-invoice`

| Route | Behaviour |
|---|---|
| `/create-invoice` | Public `InvoiceBuilderPage`; no Firestore save; `clearBuilderInvoice` on mount; PDF/print only |
| `/invoices/new` | Dashboard `InvoiceForm` + autosave; `requireOnboarding`; creates doc |
| `/invoices/[id]/edit` | Same form; loads by business ownership |

**B1 approach:** redirects `new` → `/create-invoice`, `edit` → `/create-invoice?edit=[id]`; single builder; delete account form components after import search.

## 3. Onboarding / business before save

Today every invoice action calls `requireOnboarding()` → no business ⇒ redirect onboarding.

**B1 change:** first save from builder creates a **minimal** business silently (name from invoice “From” or user display name; no placeholders). Offer dismissible onboarding prompt after first save. Do not block Download/Print/Save on onboarding.

## 4. Client name for `customerId` invoices

Create path already denormalises `clientName` / email / address. Legacy `customerId` is unused in create. History will show `clientName`; if empty and `customerId` set, resolve once and backfill denormalised fields on read/update when possible (Admin SDK). No Firestore index changes.

## 5. Status values and numbering

**Stored:** `draft`, `sent`, `viewed`, `paid`, `overdue`, `cancelled` (`types/invoice-item.ts`).

**Shown in History:** Unpaid | Paid | Overdue. Overdue = unpaid and past due date; **never stored**.

| Stored | UI |
|---|---|
| `draft`, `sent`, `viewed` | Unpaid |
| `paid` | Paid |
| `overdue` (if any legacy rows) | Overdue (or recompute) |
| `cancelled` | Treat as Unpaid or hide — **Decision:** show as Unpaid with no special badge for 3B-1 |

**Numbering:** logged-in → `invoiceService.generateInvoiceNumber` (prefix + counter). Guests keep `INV-001`.

## 6. Cross-user isolation (do not edit rules)

- Rules: `firebase/firestore.rules` — `invoiceBelongsToUserBusiness()`.
- Server: `getInvoice(id, businessId)` returns null if mismatch → 404 for edit load.
- No client Firestore invoice queries in app path.

## 7. Risks

1. Builder clears state on mount — breaks “log in to save”; must stash `ss_pending_invoice` before auth from that prompt only.
2. Template/logo/payment field shape mismatch between builder and Business/settings.
3. Autosave burning invoice numbers if create-on-every-draft — debounce and update-in-place after first id.
4. Dual guest keys (`valix_*`) — do not rename; only add `ss_pending_invoice`.
5. Many nav CTAs still point at `/invoices/new`.
6. Account vs settings surface area — payments/security placeholders removed carefully after import search.
7. Firebase `ss_auth` deferral may delay first save until auth boot — ensure save path bootstraps Firebase when hint set.
